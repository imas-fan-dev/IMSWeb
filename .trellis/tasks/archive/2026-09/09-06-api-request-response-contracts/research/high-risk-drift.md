# High-risk API contract drift

This note records current behavior for Backoffice login and Wiki mutations. It does not choose a replacement contract. Where the repository contains conflicting signals, the final section names the decision that remains with the user.

## Backoffice canonical login

### Route and handler trace

The canonical route is `POST /api/admin/auth/login`. The retained compatibility routes are `POST /api/login` and `POST /api/admin/login`. All three use the same JSON validator. The two compatibility routes also run middleware that logs `legacy_backoffice_auth_route_used`, adds `Deprecation: true`, and links to `/api/admin/auth/login` as the successor. Because that middleware runs before validation, the compatibility headers and log entry also apply to failed requests (`apps/api/src/domains/admin/backoffice-auth/routes.ts:31`, `apps/api/src/domains/admin/backoffice-auth/routes.ts:39`, `apps/api/src/domains/admin/backoffice-auth/routes.ts:55`, `apps/api/src/domains/admin/backoffice-auth/routes.ts:61`).

The handler has no controller or service layer between HTTP and persistence. It reads the validated body, calls `BackofficeAuthRepository.findUserByUsername`, verifies the password, signs the JWT, creates a refresh session, writes an audit record on a best-effort basis, sets cookies, and returns JSON (`apps/api/src/domains/admin/backoffice-auth/handlers/login.ts:24`, `apps/api/src/domains/admin/backoffice-auth/handlers/login.ts:33`, `apps/api/src/domains/admin/backoffice-auth/handlers/login.ts:46`, `apps/api/src/domains/admin/backoffice-auth/handlers/login.ts:58`, `apps/api/src/domains/admin/backoffice-auth/handlers/login.ts:68`, `apps/api/src/domains/admin/backoffice-auth/handlers/login.ts:77`).

The repository returns the complete account record. Its contract permits any string in `dept`, a nullable `producername`, and a nullable `admin_role`; the SQL implementation selects the row without projecting or normalizing those fields (`apps/api/src/ports/repositories/admin.ts:3`, `apps/api/src/ports/repositories/admin.ts:46`, `apps/api/src/infra/db/repositories/backoffice-auth-repository.ts:16`). The handler copies these values into the response as `producername`, `dept`, and `adminRole` (`apps/api/src/domains/admin/backoffice-auth/handlers/login.ts:83`).

### Request and error behavior

The request body is `{ username: string, password: string }`. Username length is 1 through 128 JavaScript code units. Password must be nonempty and no more than 1,024 UTF-8 bytes. The validator does not trim either field. It returns a new two-field object, so extra request properties are accepted but discarded before the handler (`apps/api/src/domains/admin/backoffice-auth/login-request.ts:7`, `apps/api/src/domains/admin/backoffice-auth/login-request.ts:18`, `apps/api/src/domains/admin/backoffice-auth/login-request.ts:27`).

Malformed or invalid bodies return `400 {"success":false,"message":"用户名或密码格式错误"}` through the common route validator (`apps/api/src/domains/admin/backoffice-auth/routes.ts:23`, `apps/api/src/domains/admin/backoffice-auth/login-request.ts:11`). A missing account and a bad password intentionally share `401 {"success":false,"message":"用户名或密码错误"}` (`apps/api/src/domains/admin/backoffice-auth/handlers/login.ts:33`).

Authorization differs by route. Canonical `/api/admin/auth/login` calls `login(c)` without a department requirement. `/api/login` also accepts any valid account. Only compatibility route `/api/admin/login` passes `requiredDepartment: "op"` and can return `403 {"success":false,"message":"当前账号没有管理工作台权限"}` (`apps/api/src/domains/admin/backoffice-auth/handlers/login.ts:92`, `apps/api/src/domains/admin/backoffice-auth/handlers/login.ts:98`, `apps/api/src/domains/admin/backoffice-auth/handlers/login.ts:104`).

All three paths share the login rate-limit branch and JSON body-limit branch (`apps/api/src/middleware/rate-limit.ts:312`, `apps/api/src/middleware/json-body-limit.ts:22`). Those middleware responses are part of current HTTP behavior even though they do not use the login error envelope.

### Actual success response and cookies

The API-local response interface and handler agree on this `200` payload:

```json
{
  "success": true,
  "token": "<access JWT>",
  "username": "<account username>",
  "producername": "<string or null>",
  "dept": "<string>",
  "adminRole": "<admin, super_admin, or null>"
}
```

Evidence: `apps/api/src/domains/admin/backoffice-auth/response.ts:8` and `apps/api/src/domains/admin/backoffice-auth/handlers/login.ts:77`.

Canonical login sets `ims_admin_access`, `ims_admin_refresh`, and `ims_admin_csrf`. Access and refresh are `HttpOnly`; CSRF is readable by the browser. All use `SameSite=Lax`; access and CSRF use `Path=/`, while refresh uses `Path=/api`. Access lasts 15 minutes and refresh/CSRF last 30 days (`apps/api/src/domains/admin/backoffice-auth/backoffice-auth-session.ts:13`, `apps/api/src/domains/admin/backoffice-auth/backoffice-auth-session.ts:19`, `apps/api/src/domains/admin/backoffice-auth/backoffice-auth-session.ts:32`). Compatibility login returns the same JSON but sets `token`, `refresh_token`, and `csrf_token` instead (`apps/api/src/domains/admin/backoffice-auth/handlers/login.ts:79`, `apps/api/src/domains/admin/backoffice-auth/backoffice-auth-session.ts:61`).

### Web contract and the stripping boundary

The Web owns a separate `loginSchema`. It omits `token`, requires `dept` to equal `"op"`, requires a non-null `adminRole`, and accepts `producername` as nullable or absent (`apps/web/app/lib/api/endpoints/admin.ts:81`). `loginAdmin` sends the same two request fields to the canonical route and applies that local schema (`apps/web/app/lib/api/endpoints/admin.ts:113`).

`parsed(...)` calls `schema.safeParse(payload)` and returns `result.data`, not the original response (`apps/web/app/lib/api/parsed.ts:49`, `apps/web/app/lib/api/parsed.ts:59`). This repository uses Zod 3.25.76 (`packages/contracts/package.json:140`). In that installed version, `z.object(...)` is created with `unknownKeys: "strip"`; unknown properties are not copied into the parsed object (`packages/contracts/node_modules/zod/src/v3/types.ts:2484`, `packages/contracts/node_modules/zod/src/v3/types.ts:2525`, `packages/contracts/node_modules/zod/src/v3/types.ts:2883`, `packages/contracts/node_modules/zod/src/v3/types.ts:2890`). Therefore:

- A valid `op` response loses `token` at the Web parse boundary.
- A response with `dept !== "op"` or `adminRole === null` becomes `CONTRACT_VIOLATION` instead of reaching the page.
- `producername: null` is accepted by the login schema even though `adminSessionSchema` has a different producer-name rule.

The shared admin module has no login request or response schema. Its closest contract is the session envelope, which permits `dept: string` and `adminRole: null` but models `producername` as a string with an empty-string default (`packages/contracts/src/admin.ts:4`, `packages/contracts/src/admin.ts:6`, `packages/contracts/src/admin.ts:31`).

The production login page only awaits success and navigates to `/admin`; it does not read any parsed response field (`apps/web/app/pages/admin/login/index.tsx:39`). Web documentation says browser authentication relies on same-origin cookies and forbids copying the response token to `localStorage` (`apps/web/README.md:135`, `apps/web/README.md:139`). The same paragraph still calls the CSRF cookie `csrf_token`, while runtime code prefers `ims_admin_csrf` and keeps the old name as a fallback (`apps/web/README.md:141`, `apps/web/app/lib/api/request.ts:12`).

### Test and documentation evidence

Canonical HTTP coverage requires a response `token`, decodes its HS256 header and realm claims, and asserts canonical cookies. That fixture covers only an operator account (`apps/api/tests/server/backoffice-auth-boundary.contract.test.ts:139`, `apps/api/tests/server/backoffice-auth-boundary.contract.test.ts:147`, `apps/api/tests/server/backoffice-auth-boundary.contract.test.ts:154`). Runtime contract coverage for `/api/login` requires exactly `adminRole`, `dept`, `producername`, `success`, `token`, and `username`, then uses `token` as an `Authorization` credential (`apps/api/tests/contracts/runtime-contracts.js:812`, `apps/api/tests/contracts/runtime-contracts.js:819`, `apps/api/tests/contracts/runtime-contracts.js:830`).

The Web success test mocks the narrower local contract without `token`. Its permission test mocks a canonical `403`, so it demonstrates page handling but does not prove that the canonical API rejects non-`op` users (`apps/web/tests/unit/pages/admin/login/admin-login-page.test.tsx:27`, `apps/web/tests/unit/pages/admin/login/admin-login-page.test.tsx:54`).

The operations runbook defines `/api/admin/auth/login|session|refresh|logout` as canonical and documents the canonical cookies (`docs/operations/runbook.md:85`, `docs/operations/runbook.md:89`). It also records the compatibility migration described below (`docs/operations/runbook.md:103`).

### Compatibility behavior that is already contractual

Under PRD requirement R6, the following behavior has direct code, test, or runbook evidence and must remain unless the plan explicitly authorizes a behavior change (`.trellis/tasks/09-06-api-request-response-contracts/prd.md:35`):

- Keep canonical session/refresh able to bridge a legacy cookie session during the migration window, and keep legacy refresh/logout behavior and cookie cleanup (`apps/api/tests/server/backoffice-auth-boundary.contract.test.ts:374`, `apps/api/tests/server/backoffice-auth-boundary.contract.test.ts:400`, `apps/api/tests/server/backoffice-auth-boundary.contract.test.ts:412`).
- Keep compatibility-issued JWTs realm-qualified even though they use old cookie names (`docs/operations/runbook.md:109`).
- Keep the compatibility window for at least one 30-day refresh cycle with legacy route usage at zero before route and cookie bridging removal (`docs/operations/runbook.md:121`).
- Keep `/api/admin/login`'s existing `op` gate unless a separate behavior change is approved (`apps/api/src/domains/admin/backoffice-auth/handlers/login.ts:98`).

## Wiki mutation responses

### Route, authorization, and serialization trace

Wiki routes are split across catalog, stories, and media registrars. `/api/admin/wiki/*` receives route-level Backoffice authorization. Retained `/api/wiki/*` write handlers call the same write authorization internally, except routes that attach the write middleware explicitly (`apps/api/src/domains/content/wiki/routes.ts:13`, `apps/api/src/domains/content/wiki/catalog/routes.ts:52`, `apps/api/src/domains/content/wiki/stories/routes.ts:48`, `apps/api/src/domains/content/wiki/media/routes.ts:45`).

Every write requires a canonical or legacy Backoffice cookie, a JWT department of `op` or `editor`, and a matching `X-CSRFToken`. Missing or invalid authentication returns a Wiki error JSON with `401`; insufficient department or invalid CSRF returns `403` (`apps/api/src/domains/content/wiki/handler-support.ts:75`, `apps/api/src/domains/content/wiki/handler-support.ts:106`, `apps/api/src/domains/content/wiki/handler-support.ts:126`).

There is no response controller or serializer layer after the handler. `wikiJson` runs `JSON.stringify` on the handler object without applying a shared schema (`apps/api/src/domains/content/wiki/handler-support.ts:33`). API-local interfaces describe the richer mutation payloads, and `WikiJsonResponse` unions those local shapes (`apps/api/src/domains/content/wiki/response.ts:43`, `apps/api/src/domains/content/wiki/response.ts:64`, `apps/api/src/domains/content/wiki/response.ts:154`, `apps/api/src/domains/content/wiki/response.ts:242`).

Repository results explain the handler payloads:

- Entity creates and updates return full `AgencyRecord`, `WikiGroupRecord`, or `IdolRecord` values. Entity deletes return the deleted record, conflict revision, and, for idols, soft-delete counts (`apps/api/src/ports/repositories/wiki.ts:500`, `apps/api/src/ports/repositories/wiki.ts:510`, `apps/api/src/ports/repositories/wiki.ts:442`, `apps/api/src/ports/repositories/wiki.ts:451`). The SQL repository returns the inserted agency record and returns idol card/story counts from the soft-delete batch (`apps/api/src/infra/db/repositories/wiki-entity-repository.ts:186`, `apps/api/src/infra/db/repositories/wiki-entity-repository.ts:523`).
- Category save returns either the saved `WikiCategoryRecord` or conflict state, while layout save returns a new or current revision (`apps/api/src/ports/repositories/wiki.ts:182`, `apps/api/src/ports/repositories/wiki.ts:229`, `apps/api/src/infra/db/repositories/wiki-entity-repository.ts:801`, `apps/api/src/infra/db/repositories/wiki-entity-repository.ts:877`).
- Card creation returns inserted source IDs. Source append returns inserted IDs plus a revision. Card update and source deletion return revision state; source deletion also fixes `cardDeleted` at `false` and reports cleanup candidates (`apps/api/src/ports/repositories/wiki.ts:355`, `apps/api/src/ports/repositories/wiki.ts:366`, `apps/api/src/ports/repositories/wiki.ts:394`, `apps/api/src/infra/db/repositories/story-repository.ts:382`, `apps/api/src/infra/db/repositories/story-repository.ts:520`, `apps/api/src/infra/db/repositories/story-repository.ts:673`, `apps/api/src/infra/db/repositories/story-repository.ts:722`).

### Test gap

The Wiki wire conformance suite imports only the public/admin catalog and stories read schemas. It parses four read responses and no mutation response (`apps/api/tests/wiki/wire-contract-conformance.test.ts:8`, `apps/api/tests/wiki/wire-contract-conformance.test.ts:185`, `apps/api/tests/wiki/wire-contract-conformance.test.ts:208`). That split allowed runtime fields and Web-visible fields to diverge.
