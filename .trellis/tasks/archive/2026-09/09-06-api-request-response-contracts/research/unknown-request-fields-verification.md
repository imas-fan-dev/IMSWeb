# Unknown request fields verification

## Scope and method

This scan asks one question: what would break if an existing request boundary changed from accepting unknown fields to rejecting them?

I traced `createHonoApp` through all 22 root registrars in `apps/api/src/app.ts:230-251`, then followed each nested router and each direct Wiki registrar. This covers all 47 production `routes.ts` files under `apps/api/src/domains`, plus the inline health and Wiki probe routes in `apps/api/src/app.ts:203-228`.

The filename inventory is also complete. There are exactly 34 files named `request.ts` under `apps/api/src` and no `requests.ts`. A broader `*request*.ts` search adds `admin/admin-accounts/create-admin-account-request.ts` and `admin/backoffice-auth/login-request.ts`. Active request parsing also exists in `profile-input.ts`, `news/submission.ts`, About and producer-map `data.ts`, editorial `contracts/article-input.ts` and `article-body.ts`, Wiki `handler-support.ts`, upload infrastructure, and handler-local query readers. Those out-of-band boundaries are included below.

Sender coverage includes Web endpoint modules, the pages and hooks that build their inputs, API route tests, Web endpoint tests, compatibility tests, fixtures, scripts, workflows, and documentation. Repository scripts and docs only issue bodyless health, news, map, static asset, or range requests. They add no body or query mismatch (`scripts/deployment/deploy-compose-release.sh:244-269`, `docs/operations/runbook.md:223-232`, `docs/operations/map-delivery.md:139-146`).

The API does not currently run Zod request schemas. In this report, "strip" means that a handwritten parser reads a generic object and returns only known fields. "Ignore" means that the route never validates that part of the request. "Preserve" means that an arbitrary record reaches later code.

### Wiki multipart compatibility fields

The Web sends the following field names through compatibility and upload routes:

`agency`, `idol`, `category_name`, `category_id`, `card_name`, `old_category_name`, `old_card_name`, `story_id`, `up_name`, `video_title`, `url`, `content_type_id`, `source_platform_id`, `subtitle`, `sources_json`, `expected_revision`, `cover_asset_id`, `presentation_policy`, `is_active`, `remove_image`, `image_fit`, `image_focal_x`, `image_focal_y`, `image_zoom`, `image_rotation`, `name`, and file field `image`.

Production construction is in `apps/web/app/lib/api/endpoints/wiki/index.ts:169-201,238-268,468-489,527-569,659-728`; endpoint tests assert the same fields in `apps/web/tests/unit/lib/api/endpoints/wiki.test.ts:512-532,611-612,684-689,804-811,1059-1060`.

The affected routes are:

- `POST /api/wiki/add_story`
- `POST /api/wiki/edit_story`
- `POST /api/wiki/delete_story`
- `POST /api/wiki/delete_category`
- `PATCH /api/admin/wiki/cards/:cardId`
- `PUT /api/admin/wiki/{agencies/:agencyId/icon,groups/:groupId/icon,idols/:idolId/avatar}`
- `POST/PATCH /api/admin/wiki/{agencies/:agencyId/story-cover-assets,story-cover-assets/:assetId}`
- retained `/api/wiki/agency-icon` and `/api/wiki/idol-media` media routes

`parseWikiUpload` preserves all URL-encoded or multipart text fields and allows up to 24 of them (`apps/api/src/domains/content/wiki/handler-support.ts:224-253`). Individual handlers read the legacy names. `sources_json` is a JSON-encoded nested source list; its inner fields are camel case (`upName`, `videoTitle`, `url`, `contentTypeId`, `sourcePlatformId`) and are parsed in `apps/api/src/domains/content/wiki/stories/handlers/add-story.ts:42-93`. Image transform and revision fields are decoded in `apps/api/src/domains/content/wiki/image-transform.ts:8-69`.

Strict mode will break these routes if one broad Wiki body schema is reused or if only normalized camel-case names are declared. Remediation is high: define per-operation metadata schemas, keep URL-encoded and multipart support, and validate the decoded `sources_json` value separately. A single Wiki-wide allowlist would remain too permissive and would allow fields meant for another operation.

### Projected route parameter names

Several validators deliberately rename raw path keys. These are not unknown fields, but a contract written against the projected type would reject the real Hono input:

- Fudaba guest submission `submissionId` becomes `id` (`apps/api/src/domains/community/fudaba/guest-submissions/request.ts:65-85`).
- Chronicle route `id` becomes `activityId` (`apps/api/src/domains/content/chronicle/request.ts:28-40`).
- Editorial legacy information route `id` becomes `legacyInformationId` (`apps/api/src/domains/content/editorial/request.ts:125-133`).
- Wiki `agencyId`, `groupId`, `idolId`, `assetId`, and `optionId` become a common `id` in endpoint-specific validators (`apps/api/src/domains/content/wiki/request.ts:691-724`).
- Delivery media `{ filename }` is enriched with derived URL and object key fields after validation (`apps/api/src/domains/delivery/media/request.ts:20-65`).

Remediation is low if raw route-param schemas stay separate from normalized handler inputs.

## Retired Information senders

The production Web still exposes requests to the retired admin Information API. JSON keys include `title`, `category`, `contentType`, `externalUrl`, `html`, `image`, `ids`, and `url`; multipart upload uses file field `image` (`apps/web/app/lib/api/endpoints/admin.ts:167-241`). The live page invokes these methods at `apps/web/app/pages/admin/information/index.tsx:132,168,198,230,255`.

Every `GET`, `POST`, `PUT`, and `DELETE /api/admin/information...` route now reaches a retirement handler that returns `410` without parsing request data (`apps/api/src/domains/content/information/routes.ts:25-68`, `apps/api/src/domains/content/information/handlers/retire-admin-information.ts:7-13`). Strict schemas would not create this break; the requests already fail. Remediation is high because the page must be removed or migrated to editorial community posts. These keys should not be preserved as a reason to keep the retired API permissive.

## Uninspected query and body surfaces

Routes that consume no request data currently accept arbitrary query strings by default. This includes health and compatibility probes, auth session/refresh/logout routes, admin list reads, public content reads, Fudaba owner and moderation lists, platform profile/security reads, Wiki catalog and media reads, site-package list/delivery operations, brand assets, and static site delivery. Command routes that intentionally ignore bodies include several logout/refresh operations, interaction writes with state encoded in the path, content deletes, publish/token operations, and Wiki option deletes.

This is not object stripping because no arbitrary object reaches domain code. An `emptyQuery` or `emptyBody` schema would still change wire compatibility. The production-generated `v` case above proves that empty-query enforcement cannot be applied mechanically to media routes. Treating all no-input routes as strict is a medium-to-high change because it requires a route manifest, explicit cache-buster and provider exceptions, and coverage for every registered route.

## Practical conclusion

Making every existing request schema strict now has a small visible repository break set but a broad external compatibility surface.

- Immediate known breakage: one API success test (`adminRole`), four client-concurrency calls using `request=second`, and API-generated media URLs using `v`.
- Already strict behavior: Fudaba core JSON requests, Platform account/profile/security writes, OAuth provider administration, and the five negative controls listed above.
- Highest-cost areas: editorial document bodies, Wiki JSON and multipart compatibility routes, generic multipart field handling, and OAuth callback queries.
- Lowest-risk implementation path: preserve current strip or passthrough behavior explicitly for migrated schemas, declare all supported legacy wire spellings, and reserve strict rejection for new endpoints or separately approved endpoint changes. This matches PRD R11 and avoids mixing contract ownership work with an unversioned behavior change.
