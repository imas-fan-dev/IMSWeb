# 优化社区动态响应式布局

## Goal

让用户在移动端和桌面端浏览社区动态列表时，可以快速看清每条动态的标题、左侧封面概览和必要元信息；条目整体需要均衡居中，不能因屏幕变窄而出现明显偏移、挤压或关键信息不可读。

## Background

- 用户提供的两张移动端截图显示：左侧封面与右侧文字的纵向重心不一致；只有标题、发布者和日期的条目仍占用 `176px`，上下留白过多。
- 移动端的发布者、日期和联系方式存在省略或挤压；日期占用固定宽度后，发布者常只剩几个字符。
- 现有列表把每条动态固定为 `176px` 高，并主动限制标题、摘要、发布者和联系方式的行数。这是上一次移动端适配为保证虚拟列表稳定而做的取舍，但当前行高和内部排布不再符合紧凑浏览要求。
- 用户确认今后的条目首个文本层级只承载标题；分类需要作为标签显示在右侧文字区域，不再覆盖左侧封面。
- 当前公开 `/events` 列表由移动端 Web、Tauri App 和桌面 Web 共用，调整不能破坏现有详情导航、分页和滚动行为。

## Requirements

- R1：每条动态的第一行只显示单行标题；分类作为独立标签紧随标题显示在右侧文字区域，不与标题争抢第一行。
- R2：分类标签不得再覆盖左侧封面；左侧封面概览在移动端和桌面端都需要尺寸协调、裁切稳定，并与右侧信息块共同围绕条目中心垂直对齐。
- R3：所有视口中的发布者、发布日期和可选联系方式各占一个元信息行，不再横向争抢；联系方式在超长时省略；摘要不在列表中展示，完整内容由详情页承载。
- R4：移动端不得让发布者、日期或联系方式被挤压到只剩图标或少量无意义字符；长文本不得撑破视口。
- R5：桌面端需要使用更宽但不过高的封面轨道，减少标题、发布者和联系方式的省略；发布日期仍保留在垂直居中的主信息块内，与其他元信息分别成行。
- R6：所有视口统一使用 `144px` 固定条目高度，比现有 `176px` 减少 `32px`；条目不得因标题、发布者、联系方式或图片内容而增高，加载骨架与实载条目的主要几何结构保持一致。
- R7：保留整行进入详情、分类可见性、键盘焦点、触控反馈和现有 API 数据语义。
- R8：修改范围聚焦公开社区动态列表及其直接测试，不扩展到 API、CMS 数据模型、后台管理或详情正文。

## Acceptance Criteria

- [x] 在 320px、390px 和代表性桌面视口中，标题都是右侧文字区的单行第一层；分类标签位于标题下方的右侧文字区，不占用标题行。
- [x] 左侧封面不再覆盖分类标签；封面和右侧信息块的中心线与条目中心线保持一致，相邻条目的封面尺寸和对齐方式一致。
- [x] 所有目标视口中的实载条目与加载骨架均为 `144px` 高；短内容、长内容、有无联系方式以及图片加载前后都不改变该高度。
- [x] 标题单行省略；分类标签始终可见；所有视口中的发布者、发布日期和联系方式分别占一行；列表不显示摘要。
- [x] 发布者、发布日期和联系方式不会因横向争抢而只剩图标或少量无意义字符；日期不遮挡标题、发布者、联系方式、封面或分隔线，页面无横向滚动、重叠或越界。
- [x] 超长标题、发布者和联系方式均单行省略；用户可以通过整行详情入口查看完整内容，不依赖 hover 理解条目。
- [x] 加载骨架与实载条目的轨道、间距和对齐一致；虚拟列表估高同步为 `144px`，延迟图片加载后，已渲染条目和窗口滚动位置的变化不超过现有 `2px` 门槛。
- [x] 分页、虚拟列表、整行详情导航、键盘焦点和触控反馈保持可用。
- [x] 相关单元测试、移动端 Web E2E、App E2E、桌面回归、格式化、lint 和类型检查通过。

## Out of Scope

- API、CMS 合约、迁移数据和后台编辑器。
- 社区动态详情正文、首页动态摘要和推荐卡片，除非验证证明共享样式直接受本次改动影响。
- Tauri 原生导航、标签栏或插件。
