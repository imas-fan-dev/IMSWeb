# App 导航调试复盘

## 1. 根因类别

主要属于 E（隐含假设）与 D（覆盖缺口），跨越 Router、React 提交、窗口布局与原生交互边界。

- 栏目点击不能只看已绘制的 location；新请求可能已经产生，浏览器历史也可能先于 React 提交。
- 第一次恢复到目标 Y 不代表页面高度已经稳定。Android 实包先回到 1376，反应行随后增高 88 像素，浏览器锚定将位置移到 1464。
- 文档的全局平滑滚动会影响未明确指定行为的 Router 和虚拟列表滚动。动态页加载视图开始绑定窗口时，还可能捕获上一个页面的位置。
- URL 已变不代表目标页面已经渲染。测试快速点去「我的」又返回社区，可以正确保留名片组件，因此不能同时要求一定重新请求数据。

## 2. 早期处理为什么不足

1. 把动态页标题偏移当作断言太早，增加等待后仍失败。滚动目标已被另一处写入改变，等待不会回到零。
2. 只设置局部 `scroll-behavior:auto` 后，Chromium 进入检查改善，WebKit 仍保留短加载文档的位置。虚拟器需要等真实列表就绪再绑定。
3. 跟踪版本读取计算样式和几何信息，三次均通过，无跟踪运行却曾停在 Y=9。观察本身会触发浏览器工作，不能把插入跟踪后的成功当作修复完成。
4. 最终动态页在布局阶段设置并解析滚动样式，退出还原原值与优先级；无跟踪、正常动效的五视口双轮检查全部 10 项通过。
5. 完整矩阵中剩余的请求次数失败来自测试混合了「快速往返」和「离页后延迟重载」两个前提。等待目标 H1 后，导航文件五视口 40 项全部通过；独立快速往返用例保留。

## 3. 预防机制

| 优先级 | 机制 | 具体措施 | 状态 |
| --- | --- | --- | --- |
| P0 | 状态所有者 | 用 pending 栏目与完整 URL 解释新点击；身份失效只处理个人路径；普通新导航优先 | 已实现并有单测 |
| P0 | 输入所有权 | 非零恢复保留最多五秒的高度及锚定观察；用户滚动取消，导航指针与空格激活先保存来源 | 已实现，单测及 Android 实包通过 |
| P0 | 页面生命周期 | 动态页局部滚动样式覆盖在离开时还原，Wiki 和普通 Web 保持原设置 | 单测及正常动效浏览器验证通过 |
| P1 | 区分测试前提 | 快速往返在同一事件循环触发；重载测试先等待目标页面已渲染 | 五视口导航复验通过 |
| P1 | 环境验证 | 契约入口变化后重启 Vite；确认内容渲染、客户端链接和 pageerror，不能只检查 HTTP 200 | 两个 target 已验证 |
| P1 | 平台证据 | 区分编译、安装、模拟事件和实际 UIKit/Android 操作 | 分层记录于 validation.md |

## 4. 扩展判断

窗口虚拟列表、全局滚动样式、异步数据和 Router 的组合值得检查，但本轮不扩展到普通 Web 或 Wiki 内部。后续同类工作应先说明谁写入位置、何时拥有输入、何时算内容稳定，再挑选能够区分这些条件的回归。

同分支 worktree 的基线同步也必须证明路径无交集并保存校验值；测试前确认服务确实来自目标 worktree。原生截图失败、AX 元素类型错误和模拟器图形驱动崩溃分别处理，不能直接归为导航缺陷。
