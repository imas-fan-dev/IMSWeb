# 邮件投递 Worker 化

## Goal

将注册与密码重置邮件从请求内 SMTP 投递演进为可靠的持久化后台 Worker 投递，降低 SMTP 延迟对 HTTP 请求的影响，同时保持验证码只在邮件被 SMTP 接受后才可使用的一致性保证。

## Background

- 注册当前强制邮箱验证。`POST /api/platform/auth/register` 必须提交六位验证码，只有数据库中已投递、未过期、未消费且仍有尝试次数的验证码才能创建账户。
- 当前验证码发送接口在 HTTP 请求内等待 SMTP；`202` 表示 SMTP 已接受邮件且验证码已激活，不表示仅排队。
- 初次发送失败会撤销待投递验证码；重发失败会保留旧验证码。PostgreSQL 是验证码和冷却状态的权威来源，缓存仅用于加速冷却读取。
- Web 当前不轮询投递状态。发送接口成功后立即显示“验证码已发送”并开始 60 秒倒计时。
- 仓库已有 PostgreSQL 持久任务与 in-process runner 模式，包含任务领取、租约、重试、隔离和优雅停止；当前没有独立应用 Worker 服务或队列框架。
- SMTP 配置由 Backoffice 动态管理，凭据加密存储，每次发送从 PostgreSQL 读取；Cloudflare、console 和环境变量邮件投递方式已移除。

## Requirements

- R1. 注册和密码重置的验证码生成、待投递状态与邮件任务必须在同一 PostgreSQL 事务中持久化，避免任务丢失或无任务验证码。
- R2. HTTP 请求不得等待 SMTP 网络投递完成；它只在持久任务创建成功后返回。
- R3. Worker 必须支持多副本安全领取、租约过期恢复、幂等完成和永久失败状态。临时错误在 20 秒后重试一次，每个任务最多尝试 2 次，且入队满 60 秒后不得开始新的发送尝试。
- R4. 验证码只能在 SMTP 接受对应邮件后激活；排队中、重试中或永久失败的验证码不能用于注册或密码重置。
- R5. 重发任务未成功投递前，旧验证码继续有效；新任务永久失败时不得破坏旧验证码。
- R6. 永久失败后，用户必须能够在本次后端配置的服务端冷却结束后重新请求验证码，且失败任务不能继续占用待投递锁或延长冷却。
- R7. 队列中需要发送的验证码或邮件载荷不得明文持久化；密文必须使用与 SMTP 凭据不同的加密上下文。
- R8. Worker 每次尝试发送时读取当前启用的 SMTP 配置，并继续执行公网 DNS 限制、IP 固定、TLS 1.2+ 和证书校验。
- R9. 邮件 Worker 必须作为独立 Node 进程和独立 Compose service 部署，使用与 API 相同的应用镜像但采用独立入口；API 进程只入队、不消费邮件任务。Worker 停止时不领取新任务，并等待当前任务完成或安全释放租约。
- R10. 注册仍然必须通过邮箱验证码，worker 化不得绕过、弱化或自动确认邮箱验证。
- R11. 注册与密码重置验证码申请接口只承诺任务已持久化入队。Web 不查询后台投递状态：成功入队后显示“请求已受理，请稍候查收”，并按照响应中的 `retryAfterSeconds` 冻结发送按钮；异步永久失败不主动反馈给用户。
- R12. 后台任务不得记录 SMTP 密码、验证码明文、完整邮件载荷或其他凭据。
- R13. 验证码重发间隔由超级管理员在 Backoffice “邮件服务”页面动态配置，默认值为 60 秒，只允许 30 至 600 之间的整数秒。该字段作为现有 SMTP 单例配置的一部分持久化，并沿用 CSRF、乐观并发、私有无缓存响应和无敏感值审计。注册和密码重置共享同一权威值；修改后无需重启 API 或重新构建 Web。该间隔独立于 Worker 固定的 60 秒任务发送窗口。
- R14. 验证码申请请求必须从外部 Valkey 缓存读取上次成功入队时间及当次固化的配置间隔，并计算剩余冷却时间。成功入队后更新该记录；API 的成功和冷却响应均返回后端计算出的 `retryAfterSeconds`，Web 不保留固定 60 秒 fallback。Valkey 不可用、命令超时或永不返回、键过期或被清空时，服务端必须在有界等待后取消尚未写出的缓存命令并回退 PostgreSQL 中本次请求固化的 `resend_after`：注册及已知账户使用验证码 aggregate，未知密码重置地址使用仅含用途、HMAC 收件人键和冷却时间的匿名记录。缓存故障或管理员后续修改配置不得缩短已经开始的冷却。注册与密码重置验证码申请共享专用 IP 限流预算，避免攻击者通过轮换未知地址放大匿名冷却写入。
- R15. 高频读取的重发策略以 PostgreSQL 为权威源，并通过所有 API 实例共享的 Valkey 缓存加速。缓存只保存 `resendCooldownSeconds`、单调递增的 `updatedAt` 和必要的过期信息，不保存 SMTP 凭据或密文。数据库更新成功后写穿缓存，缓存未命中时从数据库回填；并发回填和更新必须按 `updatedAt` 原子拒绝旧版本覆盖新版本。不得增加进程内 L1 配置缓存。缓存读写必须设置短时限，并将 deadline 的 abort signal 传给具体 Valkey command；缓存不可用、命令拒绝或永不返回、内容无效或同步失败时回退数据库，最终入队事务仍从数据库读取并固化权威间隔。
- R16. 当配置冷却短于 Worker 的 60 秒发送窗口时，冷却结束后的新请求必须立即取代同一用途和收件人的旧候选及旧任务，包括仍处于 `running` 的任务。旧 Worker 即使完成 SMTP 发送，也必须因 lease token 或 delivery token 失配而无法激活旧候选；旧邮件可能到达，但其中的验证码无效。若被取代的是重发候选，更早的 active code 继续按原有效期工作。

## Acceptance Criteria

- [x] AC1. SMTP 不可达时，验证码发送请求仍可在持久任务写入后及时返回，且任务可由后续 Worker 尝试恢复。
- [x] AC2. API 进程在入队提交后、SMTP 发送前退出，重启后任务仍会被领取和发送。
- [x] AC3. 两个运行实例同时处理队列时，同一投递任务只有一个有效租约所有者能够完成或标记失败。
- [x] AC4. SMTP 接受前提交验证码不能注册；接受并原子激活后可以注册且只能消费一次。
- [x] AC5. 重发任务失败时旧验证码仍可使用；初次投递永久失败后可在本次后端配置的冷却结束后重新申请。
- [x] AC6. 临时 SMTP 失败按既定退避策略重试，超过上限进入永久失败，且不会无限占用任务或延长本次后端配置的冷却。
- [x] AC7. Web 在成功入队后显示“请求已受理，请稍候查收”，并严格按照响应中的 `retryAfterSeconds` 冻结发送按钮；修改后端间隔无需修改或重新构建 Web，且不增加投递状态轮询或异步失败展示。
- [x] AC8. 数据库中不出现验证码明文；日志、审计和 HTTP 响应也不泄露验证码或 SMTP 凭据。
- [x] AC9. 注册、密码重置、SMTP 管理、队列恢复、并发租约、迁移、Web 单元和路由合约测试全部通过。
- [x] AC10. `pnpm run check` 与 `pnpm run test` 通过，preview 部署健康检查通过。
- [x] AC11. API 从 Valkey 中的上次成功入队时间和当次固化的配置间隔计算剩余冷却；缓存不可用或键缺失时，注册及已知账户回退验证码 aggregate 的 `resend_after`，未知密码重置地址回退匿名冷却记录。成功响应、HTTP `429` 和 `Retry-After` 使用一致的向上取整秒数，注册与密码重置行为一致；未知地址仍不创建验证码候选或投递任务。
- [x] AC12. Backoffice 接受 30 和 600 秒边界值，拒绝非整数、29 秒和 601 秒；未配置或迁移后的默认值为 60 秒，保存继续使用现有乐观并发和 CSRF 保护。
- [x] AC13. 两个 API 实例共享同一策略缓存；慢速旧版本回填不能覆盖新配置，更新后的正常读取无需重启即可命中新值。缓存未命中、内容无效、读写失败、命令永不返回或数据库更新后的缓存同步失败均在有界等待后回退 PostgreSQL，最终入队使用数据库中的最新间隔；策略缓存不包含 SMTP 凭据或密文。
- [x] AC14. 当冷却在旧任务发送期间结束时，新请求可以立即持久化新候选和新任务；旧任务随后发送成功也不能激活已被取代的验证码。测试同时证明旧邮件可能到达的边界，以及重发场景中更早的 active code 不受影响。

## Out of Scope

- SMTP 提供商投递回执、退信和投诉 webhook。
- 营销邮件、群发邮件和邮件模板编辑系统。
- 恢复 Cloudflare、console 或其他邮件投递提供商。
- 将所有现有对象清理任务迁移到新的邮件 Worker。
- 面向持久化外部服务配置的通用 Valkey/PostgreSQL 缓存一致性能力，包括 OAuth 和完整 SMTP 发送配置；当前任务只实现邮件重发策略的专用缓存与数据库兜底，统一方案留到下一版本。

## Decisions

- D1. 邮件任务由独立 Node Worker 进程消费，并作为独立 Compose service 部署。API 与 Worker 复用同一镜像和领域实现，但使用不同启动入口；API 不在进程内启动邮件任务 runner。
- D2. 不增加投递状态查询接口或 Web 轮询。验证码请求成功入队后，Web 按响应中的 `retryAfterSeconds` 启动倒计时并显示“请求已受理，请稍候查收”；异步投递失败是可接受风险。
- D3. 服务端冷却从成功入队时开始，时长取当前后端配置；Web 倒计时以服务端响应为准。验证码有效期从 SMTP 接受并完成数据库激活时开始。
- D4. 配置缺失、认证失败、TLS/DNS 校验失败等确定性错误立即永久失败；网络中断、连接超时和 SMTP `4xx` 等临时错误在 20 秒后重试一次。每个任务最多尝试 2 次，入队满 60 秒后不再开始发送。SMTP 已接受但响应丢失时允许同一验证码邮件重复送达。
- D5. 重发间隔在 Backoffice “邮件服务”页面动态管理，和 SMTP 设置共用现有单例配置、超级管理员权限、CSRF、`expectedUpdatedAt` 乐观并发及审计链路；允许 30 至 600 的整数秒，默认值为 60 秒。
- D6. Valkey 是请求时的首选冷却查询来源；Valkey 不可用或键缺失时回退 PostgreSQL `resend_after`。成功入队时固化当次间隔，后续配置修改只影响新入队请求。
- D7. 重发策略使用共享 Valkey L2 缓存，不增加进程内 L1。缓存只保存策略值和 PostgreSQL `updatedAt`，采用五秒 TTL，并通过按 revision 原子比较的写入阻止旧回填覆盖新配置。管理更新先提交 PostgreSQL 再写穿缓存；缓存同步失败不回滚数据库，后续读取从数据库修复，入队事务不把缓存作为最终配置判定。
- D8. 配置冷却结束后，新请求立即取代同一收件人和用途的旧候选与旧任务，即使旧任务正在发送。数据库 fencing 保证旧任务不能激活旧候选；接受在途旧邮件可能包含无效验证码。
- D9. 当前版本只实现邮件重发策略所需的专用 Valkey 缓存和 PostgreSQL 回退，不抽取通用配置缓存框架。下一版本的统一范围只覆盖 OAuth、完整 SMTP 发送配置等频繁读取的持久化外部服务配置，不扩展为业务数据的通用双写或缓存一致性系统。
- D10. 切换发布拆为 B1 和 B2。B1 只增加匿名邮件请求冷却表，公开 API、同步 SMTP、Worker 空队列和 Web 行为继续保持已部署的 Release A 语义；B1 preview 验证后，B2 才让未知密码重置地址使用该表并切换异步入队。B2 可自动回滚到 B1。B1 migration 一旦应用，pre-B1 镜像会因未知 migration 被拒绝，失败恢复必须使用 B1 镜像或现有手工数据库恢复边界。
