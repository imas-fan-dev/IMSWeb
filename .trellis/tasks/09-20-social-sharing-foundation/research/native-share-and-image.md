# Native share sheet and share-image findings

Scope: whether a scoped iOS/Android system share sheet for generated image + text + HTTPS URL can be built with what is installed, which Tauri plugin pattern in this repo to copy, what the OS will and will not let us send, and how to render two share-image layouts (vertical + link preview) with QR codes on the API's Node runtime.

Companion: `research/dynamic-card-html.md` owns the canonical public document / OG head injection. This file covers only the native handoff and the image pipeline.

## Method

- Read the repo: Tauri plugin sources, capabilities, generated Android/iOS projects, API media infra, image tooling, delivery routes.
- Executed `sharp` locally against this workspace's installed build (`apps/api/node_modules` resolution) to measure SVG rasterization and font behavior rather than assume it.
- Checked package metadata on the registries and library docs upstream for anything not installed here.
- Claims that could not be grounded are marked `unverified` with what is missing. Nothing below is asserted from memory alone.

## 1. Installed dependencies do not cover the system share sheet

Nothing in the current dependency set can present a native share sheet:

- `plugin-fs` writes and reads files. It cannot hand a file to another app.
- `plugin-opener` opens URLs through the OS handler. Its capability deliberately denies `file:`, `asset:`, `content:`, `data:`, `blob:` and `tauri:` schemes (`apps/web/src-tauri/capabilities/default.json`), so it cannot be repurposed for image handoff.
- `plugin-dialog`, `plugin-deep-link`, `plugin-geolocation` are unrelated.
- Tauri v2 has no official share plugin. The official list is Autostart, Barcode Scanner, Biometric, Clipboard, CLI, Deep Linking, Dialog, File System, Geolocation, Global Shortcut, Haptics, HTTP Client, Localhost, Logging, NFC, Notifications, Opener, OS Information, Persisted Scope, Positioner, Process, Shell, Single Instance, SQL, Store, Stronghold, Updater, Upload, Websocket, Window State. Mobile-only official plugins are Barcode Scanner, Biometric, Haptics, NFC. (verified: [v2.tauri.app/plugin](https://v2.tauri.app/plugin/))

Conclusion: a new plugin is required, either a local one or a third-party crate. Section 5 compares, and section 6 recommends the local route.

## 2. The plugin pattern to copy

The repo already contains two working mobile plugins, so a third follows an established shape. `native-image` is the closest fit: single command set, cache-directory file production, a hard file-scope rule, and an iOS Swift side.

Anatomy, using `native-image` as the template:

| Piece | File |
| --- | --- |
| Rust crate | `apps/web/src-tauri/plugins/native-image/Cargo.toml` |
| Command list + iOS path declaration | `apps/web/src-tauri/plugins/native-image/build.rs` (`tauri_plugin::Builder::new(COMMANDS).ios_path("ios")`) |
| Plugin registration, `invoke_handler`, ext trait | `.../src/lib.rs` |
| Command wrappers | `.../src/commands.rs` |
| Per-platform bridge, `register_ios_plugin` / `register_android_plugin` | `.../src/mobile.rs`; Android variant in `plugins/native-glass/src/mobile.rs` |
| Argument/result models with `serde(rename_all = "camelCase")` | `.../src/models.rs` |
| Permission declarations | `.../permissions/default.toml`, `.../permissions/autogenerated/commands/*.toml` |
| iOS Swift target | `.../ios/Package.swift`, `.../ios/Sources/NativeImagePlugin.swift`, `@_cdecl("init_plugin_native_image")` |
| Android Kotlin target | `plugins/native-glass/android/build.gradle.kts`, `android/src/main/java/NativeGlassPlugin.kt` (`@TauriPlugin`, `@Command`, `app.tauri.plugin.Plugin`) |
| Capability grant | `apps/web/src-tauri/capabilities/native-image.json` (platform filter `["iOS"]`) |
| Shell wiring | `apps/web/src-tauri/Cargo.toml` `[target.'cfg(...)'.dependencies]` + `apps/web/src-tauri/src/lib.rs` `.plugin(...)` |
| Frontend wrapper | `apps/web/app/lib/media/native-image.ts` (`invoke("plugin:native-image|prepare", ...)`) |

Key conventions worth copying:

- Capability files carry `"platforms": ["iOS"]` or `["iOS", "android"]`, so a share plugin gets its own capability rather than widening `default.json`.
- The frontend never passes a free-form path. `native-image` takes a `mediaKind` enum, the Rust layer picks the file, and the Swift side re-validates a UUID before touching the cache (`NativeImagePlugin.swift`, `release`). Tauri generates the Android Gradle wiring automatically: `plugins/native-glass/android` shows up in `gen/android/tauri.settings.gradle` without hand editing.
- The iOS side reuses `self.manager.viewController` for anything that must present UI (`plugins/native-glass/ios/Sources/NativeGlassPlugin.swift:160`). A share sheet needs exactly this.
- Result/error strings are stable slugs (`native-image-input-too-large`) that the frontend maps to Chinese copy. Keep that shape so share failures stay diagnosable.

## 3. iOS constraints

- The share sheet is `UIActivityViewController`. It presents a chooser; it cannot target one app. Every design that says "open WeChat" has to degrade to "the user picks WeChat in the sheet". This matches the PRD decision not to integrate vendor SDKs.
- `UIActivityViewController` must be presented from a visible view controller on the main thread. Use `manager.viewController` as `native-glass` does, and set `popoverPresentationController.sourceView/sourceRect` since iPadOS and "Designed for iPad" launches can run this app.
- What an app receives depends on what its share extension declares. Extensions carry an `NSExtensionActivationRule` declaring supported types (`NSExtensionActivationSupportsImageWithMaxCount`, `NSExtensionActivationSupportsWebURLWithMaxCount`, `NSExtensionActivationSupportsText`, `NSExtensionActivationSupportsFileWithMaxCount`). An extension that does not cover the supplied items is not offered. Third-party reports and a long-standing Radar (#18342403) describe this as "all provided activity items must be supported"; treat that as the working model. `unverified`: Apple's current documentation pages are JavaScript-rendered and returned no usable text to a fetch, so the strongest available sources are the developer-forum/StackOverflow consensus above plus the activation-key mechanism itself.
- The vendor SDK path proves the single-message model. WeChat's own iOS documentation marks text and multimedia as mutually exclusive in one request ("发送消息的类型，包括文本消息和多媒体消息两种，两者只能选择其一，不能同时发送文本和多媒体消息") and only exposes a single image per share through the classic API (verified quote: [developers.weixin.qq.com .../Share_and_Favorites/iOS.html](https://developers.weixin.qq.com/doc/oplatform/Mobile_App/Share_and_Favorites/iOS.html)).
- Practical consequence: expect the sheet to take an image **or** a text+URL pair, not all three. Whether a specific installed WeChat/Xiaohongshu/QQ build accepts a combined payload has to be checked on device; the design must not depend on it.
- No runtime permission is needed. Sharing a file that already lives in the app container does not touch Photos, so no `NSPhotoLibraryAddUsageDescription`. Asking for photo-library permission to share would be scope creep.
- iOS minimum is 15.0 (`apps/web/src-tauri/tauri.ios.conf.json`), well above the API floor for `UIActivityViewController`.

## 4. Android constraints

- The mechanism is `Intent.ACTION_SEND` with `EXTRA_STREAM` + a MIME type, handed to `Intent.createChooser`. Official guidance: use `ACTION_SEND` for one item, `ACTION_SEND_MULTIPLE` for several, and grant the receiving app URI read access ([developer.android.com/training/sharing/send](https://developer.android.com/training/sharing/send)).
- `EXTRA_TEXT` alongside `EXTRA_STREAM` is not honored consistently. Android documents neither a guarantee nor a prohibition, and receiver-side bugs are long-standing, e.g. [element-android#3637 "EXTRA_TEXT is ignored when receiving EXTRA_STREAM Intent"](https://github.com/vector-im/element-android/issues/3637). Treat text as best-effort when an image is attached; send text+URL alone when the copy matters.
- The FileProvider is already declared in the generated project: `gen/android/app/src/main/AndroidManifest.xml` declares `androidx.core.content.FileProvider` with `android:authorities="${applicationId}.fileprovider"`, `android:exported="false"`, `android:grantUriPermissions="true"`, and `@xml/file_paths`. `gen/android/app/src/main/res/xml/file_paths.xml` already allows `<cache-path name="my_cache_images" path="." />` and `<external-path name="my_cache_images" path="." />`. So a share plugin can call `FileProvider.getUriForFile(activity, "${applicationId}.fileprovider", file)` for a file in the app cache without touching the manifest.

  Note the `.debug` suffix: `tauri.android.conf.json` sets `debugApplicationIdSuffix: ".debug"`, so the authority string must come from `context.packageName`, never a literal.
- No storage permission is required, because the file lives in app-private cache and is exposed through a content URI with a read grant. Writing to `MediaStore` or external shared storage would require `WRITE_EXTERNAL_STORAGE` on older APIs and is unnecessary.
- Package visibility: apps targeting API 30+ need `<queries>` to *enumerate* other packages. The official page does not state that implicit intents passed to `startActivity` are filtered, and the plugin will not call `queryIntentActivities`, so no `<queries>` entry is expected. `unverified` for the enumeration case; verify on a device if a future feature wants to detect "is WeChat installed".
- The leftover `file_paths.xml` names (`my_images`, `my_cache_images`) are Tauri template defaults. Adding a narrower `<cache-path name="share" path="share/" />` would tighten the grant surface at the cost of a generated-file edit.

## 6. Recommended plugin shape

Name: `native-share`, path dependency under `apps/web/src-tauri/plugins/native-share`, `platforms: ["iOS", "android"]` capability.

Command surface, deliberately one command:

```
plugin:native-share|share
args: { imageId?: string, text?: string, url?: string, mode: "image" | "link" }
result: { outcome: "completed" | "dismissed" }
```

Rules that keep the surface small and safe:

- `imageId` is a UUID. The native layer rebuilds the path as `<cache>/share/<uuid>.png`. The frontend never supplies a path, mirroring `native-image`'s `release` validation.
- The frontend writes the generated bytes into `$CACHE/share/<uuid>.png` with `plugin-fs`, which requires a new `fs:scope` allow entry for `$CACHE/share/**` in the share capability. The share capability should not inherit the broader `$CACHE/native-image/**` grant.
- `mode` picks the payload shape: `image` sends the file only (WeChat, Xiaohongshu), `link` sends text + URL (QQ, copy-friendly targets). This is the cheapest way to respect the iOS activation-rule and Android `EXTRA_TEXT` problems without per-app code.
- Reject `tauri://`, `asset://`, `file://` for `url` in Rust before reaching native code. A URL that only resolves on the device must never leave it (PRD acceptance criterion).
- Return dismissals as a normal result, not an error, so "user cancelled" is not surfaced as failure.
- Cleanup: reuse the `native-image` expiry idea (`cleanupExpired`) or delete the temp file after the share result.

## 7. Server-side image generation: sharp is present and works, with one hard caveat

Executed locally against the installed `sharp` 0.35.4 build in this workspace:

```
sharp version 0.35.4 vips 8.18.6
svg input format: file/buffer/stream, suffix .svg/.svgz  (output formats: png, jpeg, webp, ...)
svg -> png: rendered, 1507 bytes for a 120x40 sample
```

So an SVG template → PNG/JPEG/WebP raster is available today with no new dependency, and the existing `apps/api/src/infra/media/sharp/image-processor.ts` already establishes the `sharp`-in-infra, port-mediated pattern to extend.

The caveat is text. SVG `<text>` is rendered by librsvg through fontconfig and the system font set:

- Two renders with different `font-family` values came back byte-identical in my test (a bogus family produced the same 1762 dark pixels as `Noto Sans CJK SC`). Font resolution is therefore happening outside the SVG and depends on the host, not on the markup. This machine has 87 CJK-capable fonts; the API container has none.
- Upstream confirms the failure mode is not graceful: [lovell/sharp#4374](https://github.com/lovell/sharp/issues/4374) reports a segfault when rendering `<text>` with no fonts installed, [#3393](https://github.com/lovell/sharp/issues/3393) reports the same class of crash, and [Ghost's fix](https://github.com/TryGhost/Ghost/pull/26863) was to add `fontconfig` to the production image.
- `apps/api/Dockerfile` installs only `g++ make python3` on `node:24.18.0-bookworm-slim`. Whatever the layout approach, do not ship `<text>` into that image unexamined.

## 8. Three ways to render Chinese text, with tradeoffs

1. **Keep SVG `<text>`, fix the image.** Add `fontconfig` plus a CJK font package to `apps/api/Dockerfile`, then rely on `<text>`/`<tspan>` for wrapping and alignment. Least layout code, standard SVG semantics. Costs image size (`fonts-noto-cjk` is tens of MB; a subset font cuts that) and keeps a system-level dependency that can regress silently.
2. **Convert text to vector paths.** Load a bundled subset font with `opentype.js` 2.0.0 (pure JS, no native deps, CJS `./dist/opentype.js` + ESM `./dist/opentype.mjs`, verified registry metadata) and emit `<path>` elements. Rasterization then needs no fonts at all, output is deterministic, and the container stays as it is. Costs a font file in the repo plus hand-rolled line breaking and text measurement.
3. **satori + a renderer with explicit fonts.** `satori` turns a JSX-ish tree into SVG and requires font data as a Buffer; TTF/OTF/WOFF only, no WOFF2 ([vercel/satori README](https://github.com/vercel/satori)). Rasterizing satori's output through `sharp` reintroduces the fontconfig dependency unless `@resvg/resvg-js` 2.6.2 is used, which accepts `font.fontFiles` and `loadSystemFonts: false`. Most ergonomic layout model (flexbox, wrapping), but it adds two dependencies for a job that currently needs none.

Recommendation for the first phase: option 2 if the two layouts use a fixed set of strings and one or two faces, because it removes an entire class of container-level failure and keeps review of the output deterministic. Option 1 otherwise, with a subsetted CJK font and a build-time font-presence assertion. Option 3 only if the layouts become genuinely content-driven (long intros, multi-line names) and the team accepts the extra native dependency.

## 9. QR generation

Nothing QR-related is installed. Options checked:

| Option | Facts | Fit |
| --- | --- | --- |
| `qrcode` (soldair) 1.5.4 | MIT, `engines.node >= 10.13.0`, deps `pngjs`, `yargs`, `dijkstrajs`. `toString(text, { type: "svg" })` returns SVG XML; `toFile` supports png/svg/utf8; `toDataURL` is PNG-only on the server; `toBuffer(text, opts, cb)` exists in `lib/server.js` and dispatches to the renderer's `renderToBuffer`. Options include `margin` (default 4), `width`, `errorCorrectionLevel` L/M/Q/H | Best fit. SVG output embeds into a layout template as paths, so it renders under any rasterizer |
| `@paulmillr/qr` 0.3.0 | zero runtime deps, ESM, outputs ascii/term/gif/data-url/svg | Viable modern alternative; unverified engines field |
| `qrcode-generator` | not verified in this repo | Skip unless the above disappoint |

Prefer the SVG output and inline it into the layout SVG. That keeps one rasterization step (sharp), avoids `pngjs` in the render path for compositing, and makes the QR testable as text.

Delivery: the QR must encode the canonical HTTPS card URL, not a short link (PRD decision). Generate it from the same resolved origin the API uses for public delivery so the App and Web produce identical codes.

## 10. Two layouts from one projection

Concrete shape, reusing the PRD's constraint that both layouts share content:

- Input: one public projection (display name, producer, intro excerpt, theme color, front image) plus the canonical URL. No owner-only, revision, moderation, or media-copyright fields.
- Template A, vertical: roughly 1080x1440 (3:4) or 1242x1660, full-bleed theme color, front image, name, producer, QR bottom-right.
- Template B, link preview: 1200x630 (1.91:1), thumbnail-safe, QR optional but harmless.
- Both templates are pure functions of the projection, so they can be unit-tested as strings and diffed.
- Placement: an infra renderer beside `apps/api/src/infra/media/sharp/image-processor.ts` (or a new `share-image` module) behind a port, consumed by a domain handler under `apps/api/src/domains/community/fudaba/directory/` for the public read and by a delivery handler for the image bytes. Register in `apps/api/src/app.ts`; path constants belong in `packages/contracts/src/paths.ts`.
- Public eligibility must be the same predicate as the JSON read and the public document: `requireFudabaPublicRead` (`apps/api/src/domains/community/fudaba/access-policy.ts`) returns 404 when `IMS_FUDABA_PUBLIC_READ_ENABLED` is false, and the card must exist and be publicly eligible. The sibling `dynamic-card-html.md` reaches the same conclusion for the HTML document: one predicate, three surfaces, 404 when absent or ineligible.
- Caching: derive an ETag from the projection fields that affect the image (a content hash), and set `Cache-Control` with revalidation. Do not cache past an eligibility change. Generation is cheap (sharp rasterization of an SVG is milliseconds), so an R2-published derivative is optional and only pays off if crawler traffic is heavy; if derivatives are stored, the same cache-busting hash must appear in the URL.

Note: `apps/api/src/domains/community/fudaba/directory/routes.ts` currently exposes `/cards`, `/cards/:cardId/reactions`, `/offices`, `/offices/:officeSlug`, `/series`, `/map/*` under `requireFudabaPublicRead`. There is no `/cards/:cardId` detail read. A share foundation needs that single-card public read before any share URL can be stable.

## 11. Risks, ordered by how likely they are to bite

1. Combined image + text + URL payloads are not portable. iOS extension activation and Android `EXTRA_TEXT` handling both cut items. Mitigation is the `mode` split in section 6 plus the PRD's save-image/copy-copy fallback; device testing on WeChat, QQ and Xiaohongshu is the only proof.
2. CJK text rendering will break in the production image unless fonts and fontconfig are addressed, and the failure is a segfault or tofu, not an exception. Mitigation is section 8.
3. The vertical and preview images can drift apart if they are built as two independent templates. Mitigation: one projection type, two template functions, one test that asserts the QR payload is identical between them.
4. The App can hand the sheet a file the frontend wrote to an unscoped path if the capability grants too much. Mitigation: UUID-id command, `$CACHE/share/**` scope, scheme rejection for `url`.
5. Stale third-party plugin (0.0.1, 2024) would import unreviewed Swift/Kotlin. Mitigation: local plugin.
6. Crawler-facing preview metadata is a separate delivery problem, owned by `dynamic-card-html.md`. If that route is not built, the preview image has no consumer and the share sheet is the only beneficiary.
7. Android debug and release builds have different application ids (`.debug` suffix), so a hardcoded FileProvider authority will fail in one of them.

## 12. Recommended sequence

1. Public single-card read + canonical URL. Add `/cards/:cardId` (or equivalent) under `requireFudabaPublicRead`, define the projection in `packages/contracts`, add the public path helper. Nothing else can be stable before the URL is.
2. Share-image renderer, text-free first. Build the two SVG templates with theme color, image, QR and no text, rasterize with the installed `sharp`, verify byte-identical QR payloads across layouts. This isolates the font decision.
3. Decide the text route (section 8) and implement it. Add the CJK font strategy and a test that asserts non-blank ink in a known text region, so a font regression fails the suite instead of shipping tofu.
4. Image endpoints. Serve both layouts with ETag/revalidation, gated by the same eligibility predicate, 404 on ineligible or disabled public read.
5. Web share surface. Download image, copy text, copy URL, no vendor SDKs.
6. `native-share` plugin. Rust crate + iOS Swift + Android Kotlin, capability, permission files, frontend wrapper, error slugs.
7. App share surface. Fetch the image over HTTPS, write to `$CACHE/share/<uuid>.png`, invoke `share` with `mode: "image"` or `"link"`, fall back to step 5's manual actions on failure or dismissal.
8. Device pass. WeChat, QQ, Xiaohongshu, and the plain system targets on both iOS and Android, checking what each actually receives.
9. Crawler metadata consumption, coordinated with the `dynamic-card-html.md` route work.

## 13. Verification ideas

- Unit: template functions produce stable SVG for a fixture projection; the QR payload string is identical for both layouts; owner-only fields never appear in template input or output.
- Unit: eligibility predicate returns 404 for disabled public read, deleted card, and ineligible card across the JSON read, the image endpoint, and the document route.
- Rust: `share` rejects missing `imageId` and non-UUID ids, rejects `tauri://`/`asset://`/`file://` URLs, and maps a dismissal to `outcome: "dismissed"`.
- Frontend: `plugin-fs` write is scoped to `$CACHE/share/**`; the wrapper falls back to download + copy when `invoke` throws or the plugin is absent (web build).
- Rendered-image assertion: rasterize a fixture with known Chinese text and assert dark-pixel count above a floor, so a missing-font environment fails CI rather than producing blank images.
- Build assertion: the Docker image used by `apps/api` contains the font the renderer names, or the renderer is path-based and needs no font.
- Device matrix: for each of WeChat, QQ, Xiaohongshu, confirm whether the payload arrived as image, as text+link, or as neither, and confirm the fallback path is reachable when it fails.
