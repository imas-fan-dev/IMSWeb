# 设计社交分享基座与名片分享

## Goal

建立可扩展的社交分享基座，让公开内容可以通过一致的入口生成可分享链接、平台所需素材和降级操作。首期接入名片分享，支持微信、QQ、小红书和单纯链接分享；后续可在不复制渠道逻辑的前提下接入动态等其他公开内容。

当前实施切片先统一名片墙的浏览入口：列表保持紧凑，详情 Dialog 承载完整图片、公开参数、认领与 emoji 交互，并成为后续单名片分享的入口。

## Background

- Web 与 Tauri App 都需要发起分享；离开 App 的 URL 必须是浏览器可访问的 HTTP(S) 地址。
- 仓库当前仍能看到旧名片墙 `Namecard` 与 Fudaba 交换名片 `FudabaCard` 两套实现，但产品设计以旧名片已全面迁移到 Fudaba 为准。
- Fudaba 公开卡片已有制作人、展示名、简介、主题色、正反面图片和互动数据。
- Fudaba 目前只有公开列表 API，没有稳定的公开单卡详情页面或公共单卡 API。
- 仓库已有公开媒体交付、Fudaba 公开资格判断和 `resolveShareableOrigin()`，但没有通用分享领域、短链、二维码、分享图、Open Graph 或平台适配器。
- Tauri 外壳已有 opener、dialog 和 fs 插件，但没有可发送图片、文案与链接的系统分享插件；App 侧需要增加受控的移动端分享能力。
- 微信 H5 JS-SDK 可配置微信内置浏览器的分享菜单内容，但不能从普通网页主动拉起分享面板，并要求已认证帐号、业务域名和签名配置。
- QQ 网页分享主要支持 URL 类型内容；更完整的消息类型和客户端拉起能力依赖移动端 SDK。
- 小红书官方一键分享依赖 iOS、Android 或 HarmonyOS 客户端 SDK，并要求应用登记、审核和 AppKey；没有与之等价的通用 H5 分享能力。

## Requirements

### Product requirements

- 分享能力按“分享对象”和“分享渠道”解耦。首期对象只支持新的 Fudaba 名片，后续可增加动态等公开对象，而无需重写微信、QQ、小红书和链接渠道逻辑。
- 首期提供四个明确入口：微信、QQ、小红书、复制或系统分享链接。
- 点击列表中的名片正面、背面或 emoji 摘要时，先打开详情 Dialog。详情同时展示全部已有 emoji 反应、卡片正反面图片，以及适合公开展示的名片参数。认领操作也从详情发起，Web 与 Tauri App 保持一致的可见内容。详情为后续名片分享预留接入位置，本轮不提供尚不可用的分享按钮。
- 移动端列表最多展示 3 个 emoji 反应，按反应数量由高到低排列；数量相同则保持接口返回顺序。桌面端列表展示全部已有反应。列表中的反应仅作摘要，点击摘要进入详情；全部反应、添加反应与点击已有反应的操作集中在详情中。列表本身不展示添加反应的选择器。
- 外部分享 URL 打开独立的公开名片详情页，不以列表 Dialog 或列表分页状态作为落地内容；详情页与列表 Dialog 展示同一公开内容。
- 详情 Dialog 只展示公开投影，不读取或展示 owner-only、审核和媒体版权字段。
- 每次分享都基于稳定的公开对象标识和 canonical URL，不依赖列表页当前分页、弹窗状态或 App-only 路由。
- 首期分享图使用同一套公开投影生成两种版式：小红书手动发布使用竖版分享图，微信、QQ 链接预览使用适合缩略图的预览图；两者二维码都指向同一名片 canonical URL。
- Web 与 Tauri App 使用同一套分享意图和结果模型；App 生成的外部链接不能包含 `tauri://` 地址。
- App 侧在系统能力允许时调用原生分享面板，按接收端能力交接分享图或文案与 canonical URL；不能假定目标应用同时接收三者。微信、QQ、小红书按钮共享系统交接能力，不承诺绕过系统面板直达指定应用。
- Web 侧不尝试直接唤起微信、QQ 或小红书，提供分享图下载、分享文案复制和 canonical URL 复制，由用户手动保存并发布。
- 系统分享不可用或目标应用无法接收完整组合时，降级为保存分享图并复制文案与链接。
- 分享对象下架、删除、关闭公开读取或失去公开资格后，分享入口和公开落地页不得继续泄露私有内容。
- 分享失败、用户取消、剪贴板不可用、图片生成失败时应有明确且可恢复的降级行为。

### Extensibility requirements

- 分享基座使用稳定引用解析公开分享投影，而不是复制名片领域的完整记录或 owner-only 字段。
- 每个分享对象适配器负责标题、摘要、主图、主题色、公开资格和 canonical 路径；渠道层不硬编码 Fudaba 发布状态。
- 渠道能力需要可声明，至少能区分链接、文案、分享图、二维码和系统原生分享，以便未来调整平台能力而不改变对象契约。
- 公开 JSON wire format 由 `@imsweb/contracts` 提供；共享公开路径由 `@imsweb/contracts/paths` 统一定义。

### Public delivery requirements

- 名片需要可匿名访问的稳定详情地址，并与现有 Fudaba 公共读取开关和公开资格规则保持一致。
- 公开落地页需要为浏览器用户提供完整名片内容，并为微信、QQ 等抓取端提供可用的标题、摘要、canonical URL 与预览图片元数据。
- 公开投影不得暴露 revision、审核状态、媒体版权状态或其他 owner/moderation 字段。

## Acceptance Criteria

- [ ] 已定义与具体业务对象解耦的分享对象、渠道能力、分享意图和分享结果契约。
- [ ] 点击列表名片的任一面或 emoji 摘要后先打开详情 Dialog；详情可同时查看全部 emoji 反应、正反面图片和列表已有的公开展示参数，并完成可用的认领操作。关闭后回到原列表上下文。
- [ ] 移动端列表最多展示按数量排序的 3 个只读反应摘要；桌面端列表展示全部已有反应。列表不提供添加反应入口，完整互动集中在详情中。
- [ ] 点击详情中的正面或背面图片后进入现有全屏缩放预览；关闭预览返回同一张名片的详情，关闭详情再返回原列表位置与触发元素。
- [ ] 详情只展示从列表打开的名片，没有上一张、下一张按钮或“第 N / M 张”位置指示，也不会在后台读取相邻页。列表自身仍可分页。
- [ ] 后续分享功能接入详情时可从详情发起分享；本轮详情切片不展示不可用的分享按钮。
- [ ] 已定义首期名片的稳定公开详情 URL、匿名读取行为、canonical URL 和不可见状态行为；从外部打开该 URL 进入独立详情页，不会自动打开列表 Dialog。
- [ ] Web 与 Tauri App 能从名片入口打开同一分享界面，并展示微信、QQ、小红书和链接四种选择；界面根据运行环境给出可执行操作。
- [ ] App 在系统支持时能将适用的分享图或文案与 canonical URL 交给系统分享面板；不保证目标应用同时接收三者。系统分享不可用或负载不兼容时提供保存与复制降级，用户取消不会被报告为错误。
- [ ] Web 能下载分享图并复制文案与 canonical URL，不依赖微信、QQ 或小红书 SDK。
- [ ] 复制或系统分享得到的 URL 在普通浏览器中可访问，不会产生 `tauri://` 或仅限登录用户的地址。
- [ ] 竖版分享图和链接预览图均来自同一公开投影，图中的二维码均解析为同一 canonical URL，不依赖短链服务。
- [ ] 公开名片分享页输出约定的社交预览元数据，且预览内容只来自公开投影。
- [ ] 名片下架、删除、公开读取关闭或失去公开资格后，公开详情与分享派生内容按约定失效。
- [ ] 分享基座具备新增第二类分享对象的适配点，并通过测试替身证明无需修改既有渠道实现。
- [ ] 合同、路径、API、Web 单元测试和跨端路由测试覆盖正常流程、取消、失败与降级行为。

## Out of Scope

- 当前 Dialog 切片不实现独立公开单卡详情页、公开单卡 API、OG HTML、分享图、二维码、渠道操作或 Tauri 原生分享；这些保留在本任务的后续阶段。
- 当前 Dialog 切片不扩充列表 wire format，也不通过 owner-only 或审核接口补齐详情字段。
- 实现动态发布或动态详情页；本期只保留接入扩展点。
- 旧 `Namecard` 分享适配、旧名片 URL alias 和双模型兼容；旧数据迁移由既有名片迁移工作负责。
- 建立公开用户主页或公开平台 profile。
- 接入微信、QQ 或小红书账号授权、内容代发、指定应用直达或第三方开放平台审核流程。
- 可管理短链、点击统计、链接过期、短码撤销与自定义短码。
- 分享推荐、社交关系、排行榜和增长运营系统。

## Technical Notes

- `FudabaCard` 已具有首期分享展示所需的大部分公开字段，并且是唯一的首期名片分享模型。
- Fudaba 公开目录由 `IMS_FUDABA_PUBLIC_READ_ENABLED` 门控，关闭时返回 404。
- `resolveShareableOrigin()` 已处理浏览器与 Tauri App 的外部 URL origin。
- 微信、QQ、小红书网页环境没有统一可靠的直接发布协议，渠道设计不能假设所有平台都能由网页直接发布。
- 渠道能力需要按运行环境探测。微信内 H5、普通浏览器、Tauri WebView 和未来原生壳可能执行不同动作，但应消费同一份公开分享投影。
- Tauri 原生分享需要独立的窄权限插件。iOS/Android 对图片、文案和链接组合的接收能力不一致，完整组合必须以设备验证为准，不作为发布保证。
- 生成中文分享图时必须显式解决 API 容器中的字体依赖；现有 `sharp` 能将 SVG 转为 PNG，但容器不包含 CJK 字体。

## Decisions

- 首期名片分享只接入新的 Fudaba 名片模型。当前截图中的「制作人名片墙」读取 `fudaba_cards` 的兼容来源名片列表；本轮详情切片以该列表已有数据为边界，不因此扩大首期分享对象范围。
- 名片列表先新增卡片详情 Dialog，收纳认领和完整 emoji 交互；移动端列表只展示按数量排序的最多 3 个只读 emoji 摘要，桌面端可展示更多。后续分享入口接入详情。外部分享 URL 打开独立的公开名片详情页，两种视图复用公开内容。
- 分享基座不承担旧 `Namecard` 的兼容或迁移；设计上按旧名片已全面迁移到 Fudaba 处理。
- App 首期使用操作系统分享能力把内容交给外部应用，按图片或文案加链接选择可接受的交接方式；Web 首期使用下载分享图与复制文案、链接的手动流程。
- 首期不接入微信、QQ 或小红书官方 SDK，也不把平台审核作为上线前置条件。
- 首期使用稳定的名片 canonical URL 和对应二维码，不建设独立短链服务。
- 首期使用两种分享图版式：小红书竖版与微信、QQ 链接预览版；两者复用内容与生成管线。
- 公开单卡详情采用技术路线 A：生产 Hono 在 canonical URL 返回含该卡社交预览元数据的 Web SPA 文档；浏览器打开独立详情页。用户已批准此技术路线，但明确要求暂不实施。
- 当前选定先做范围 A：列表内详情 Dialog 及移动端 emoji 折叠，不在这一切片实施独立公开详情页、OG HTML、分享图或原生分享。
- 列表图片不再直接进入全屏缩放预览。列表先打开详情，详情中的图片再进入现有全屏预览；关闭全屏预览回到详情，关闭详情回到列表。
- 详情 Dialog 固定展示列表选中的名片，不提供跨名片切换或位置指示。全屏预览只负责这张名片的正反面、缩放、拖动和图片重试；关闭后回到该名片详情。列表分页保持独立。
- 用户后续明确要求移除详情的上一张、下一张与位置指示；此次实施按该决定调整已写好的 Dialog 切片。
