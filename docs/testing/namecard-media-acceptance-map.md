# 名片图片人工验收：链路归并与最小用例集

> 文档类型：测试计划
> 状态：Active
> 权威来源：`apps/api/src/domains/community/fudaba/`、`apps/api/src/domains/community/namecards/`、`apps/api/src/infra/db/repositories/`、`apps/web/app/pages/`、`docs/architecture/namecard-media-execution.md`

目标：在测试环境里用最少的操作覆盖「七个列表 + 对应窗口」的名片图片显示。图片正确性由
「写入链路 × 状态迁移 × 读取作用域」决定，同一条链路只测一次，不同链路各测一次。

## 1. 七个观测面

| 编号 | 列表 | 数据接口 | 可打开的窗口 | 图片断言点 |
| --- | --- | --- | --- | --- |
| L1 | 属主「我的名片」 | `GET /api/community/exchange/me/cards` | `CardWorkspace` → 编辑画廊、详情窗、全屏预览（含 `pendingPages`） | 瓦片、画廊 `previewUrl`、全屏 `url`、待审图只在属主可见 |
| L2 | 名片墙 | `GET /api/cards` | `NamecardDetailDialog` → `NamecardPreview` | 瓦片 `thumbUrl`、页签、全屏原图、页数角标 |
| L3 | 用户主页 | `GET /api/users/:handle/cards` | 同上复用 | 与 L2 相同，但只应出现该用户已发布卡 |
| L4 | 后台投稿审核 | `GET /api/admin/cards` | 投稿审核窗（`DiffArtwork` + `ReviewCardPreview`） | 左=线上、右=待审；单面卡不得出现幽灵背面 |
| L5 | 后台认领审核 | 审核队列（claims） | `ClaimReviewDialog` | 老卡与目标卡两套图正确、旋转后的图是待审版本 |
| L6 | 后台补充审核 | 审核队列（supplements） | `SupplementReviewDialog` | 申请里的页面集合与旋转标注正确 |
| L7 | 后台反馈队列 | 反馈列表 | `NamecardManageDialog` | 反馈所属卡的图与列表瓦片一致；管理保存后不串图 |

> 后台「管理」入口与 L4 共用 `/api/admin/cards` 和 `NamecardManageDialog`，本文件把管理操作归到
> L4/L7 观察，不单独算第八个列表。「用户管理界面」按个人中心的「我的名片」理解；如果指后台账号
> 管理页，该页不展示名片图片，不纳入本验收。

## 2. 判定标准（所有用例共用）

- 瓦片：`pages[].thumbUrl`（或旧字段回退）返回 200，不出现错误占位或旧图。
- 详情/审核缩略预览：`previewUrl`；审核窗左右版本的页面集合与页序正确。
- 全屏：`pages[].url` 为原图（不带 `w`），页签顺序 = `display_order`，单面卡只有正面页签。
- 待审状态：属主 `draft=1`、后台 `live|draft` 两种作用域各看一次；公开面绝不能拿到待审图。
- 页数变化后：列表页数角标、页签数量、全屏可翻页数三者一致。
- 旋转后：同一槽位出现新版本（缓存不命中旧图）；未旋转的槽位版本不变。

## 3. 链路归并（38 条原始操作 + 复审矩阵 → 14 条链路）

### 属主操作

| 原始条目 | 链路 | 处理 |
| --- | --- | --- |
| 1 新建双面 / 2 新建单面 / 3 新建多页 | `CH-CREATE` | 同一 `POST /me/cards`；只需按页数边界测三次（1 页、2 页、≥3 页），角色推导不同 |
| 4 新建时旋转 | `CH-CREATE-ROTATE` | 与新建同接口，`create-card` 的 `rotations` 分支；并入 C4 一次 |
| 5 修改正面/背面 | `CH-SET-REPLACE` | 同一 `PUT /me/cards/:id/media`（整组提交） |
| 6 单面卡新增正面/背面 | `CH-SET-ADD` | 同上，页数 1→2 |
| 7 新增中间页 | `CH-SET-ADD` | 同上，页数 2→3+ |
| 8 新增正/背面导致原正/背面变中间页 | `CH-SET-ROLE-SHIFT` | 同上，断言的只是页序与角色 |
| 9 删正面/背面 / 10 删中间页 / 11 删多页正/背面 | `CH-SET-DELETE` | 同一整组提交，页数减少；角色重排 |
| 12 调换中间页顺序 | `CH-SET-REORDER` | 同一接口且不带新文件，命中「仅顺序变化免审」分支 |
| 13 旋转正/背面 | `CH-SET-ROTATE` | `rotations.front/back` |
| 14 旋转中间页 | `CH-SET-ROTATE` | `rotations.middles[i]`，与 13 同一个 handler，建议同一次提交里一起转 |
| 15 删除名片 | `CH-DELETE` | 软删除，读侧消失 |
| 16 非公开可见 | `CH-VISIBILITY` | `visible=false`，只影响公开读 |
| 17 还原图片撤回提交 | `CH-WITHDRAW` | 提交整组图后再还原为提交前集合；待审集合清空 |

### 用户操作

| 原始条目 | 链路 | 处理 |
| --- | --- | --- |
| 1 补充信息（仅文本） | `CH-SUPPLEMENT-TEXT` | 不写媒体；只验证队列与窗口出现，不做图片断言 |
| 2 补充信息 + 旋转正/背面 | `CH-SUPPLEMENT-MEDIA` | 补充载荷带 `rotations`；审核时 `rotateReviewedArtwork` 生成新页面对象 |
| 3 认领无主卡 | `CH-CLAIM` | 认领本身不写媒体；通过后才复制/绑定图片 |
| 4 认领 + 旋转正/背面 | `CH-CLAIM-ROTATE` | 与 2 共用服务端旋转实现，但审批落库路径不同（claim completion） |
| 5 反馈无主卡 | `CH-FEEDBACK` | 不写媒体；只验证反馈卡与列表瓦片绑定正确 |

### 管理操作

| 原始条目 | 链路 | 处理 |
| --- | --- | --- |
| 1 通过新建审核 | `CH-REVIEW-SUBMIT-APPROVE` | 首审：卡从待审变已发布 |
| 2 驳回新建审核 / 3 锁定新建审核 | `CH-REVIEW-SUBMIT-DECIDE` | 首审：不提升媒体；确认待审图不出现在公开面 |
| 复审：通过 / 驳回 / 锁定已发布卡的修订 | `CH-REVIEW-REVISION` | 同一审核入口，但卡已 published；通过才把 pending 页提升为 live，驳回/锁定保持线上版本（矩阵见 4.1） |
| 4 锁定已通过卡 / 5 解锁 | `CH-LOCK` | 纯状态位，媒体不变；图片只看一次即可 |
| 6 通过补充 / 7 驳回补充 | `CH-REVIEW-SUPPLEMENT` | 通过时 `completeCardSupplementReview` 带 `pages` 同步 |
| 8 通过认领 / 9 驳回认领 | `CH-REVIEW-CLAIM` | 通过时 claim completion 写入目标卡并同步页面 |
| 10 旋转用户/游客名片正/背面 | `CH-REVIEW-ROTATE` | 审核窗旋转（`rotateReviewedArtwork`）或管理窗 `update-admin-namecard` 旋转；两条入口写同一类页面对象 |
| 11 旋转中间页 | `CH-REVIEW-ROTATE` | 管理窗按 `middles` 数组提交（与中间页顺序对齐）；审核窗旋转仍只覆盖 front/back |
| 12 删用户/游客正/背面 | `CH-ADMIN-MEDIA-DELETE` | 管理窗整组提交减少页面 |
| 13 删用户名片中间页 | `CH-ADMIN-MEDIA-DELETE` | 与 12 同一条整组提交 |
| 14 删用户名片 | `CH-ADMIN-DELETE` | 软删除，所有列表消失 |
| 15 已通过→已驳回 | `CH-STATUS` | 公开面消失；管理/反馈仍可见 |
| 16 已隐藏→已通过 | `CH-STATUS` | 公开面重新出现，页面版本不变 |

## 4.1 复审（已发布卡修订）的通过 / 驳回组合

复审与首审共用审核入口，但前提不同：卡已发布，修订内容在 pending 页与 `pending_*` 列；
审核期间公开面继续服务 live 版本。

| 复审内容 | 通过 | 驳回 / 锁定 |
| --- | --- | --- |
| 仅文本（无图） | 页面行与版本不变，公开面图片不变 | 页面行不变；文本回到原值 |
| 仅替换图片（页数不变） | pending 页整体提升，公开面换新版本 | 公开面保持旧版本 |
| 加页 / 删页 | 旧 live 页整组被待审页替换，页数角标同步 | 旧 live 页保持，待审页不得泄漏到公开面 |
| 旋转正/背/中间页 | 被旋转的槽位换新版本，其余槽位版本不变 | 所有槽位保持旧版本 |
| 图片 + 文本 | 两者一起提升 | 两者都不生效 |
| 仅调换页序 | 不进复审：直接直写页序 | — |
| 复审期间属主「还原图片」撤回 | 待审页清空，队列消失，公开面不变 | — |
| 驳回后重新提交 | 新修订覆盖 pending 页，再次通过时只提升新集合 | — |

对应用例：

| 用例 | 前置 | 操作 | 观察重点 |
| --- | --- | --- | --- |
| C17 复审通过（图片修订） | 已发布 3 页卡 | 属主替换正面 + 新增中间页 + 旋转中间页 → 提交 → 后台通过 | L2/L3 立即是新版本；旧 live 页被整组替换；L4 队列移除；页数角标一致 |
| C18 复审通过（仅文本） | C17 的卡 | 只改简介提交 → 后台通过 | 页面行与 `object_version` 全部不变；L2/L3 不闪回旧缓存 |
| C19 复审驳回 / 锁定（图片修订） | C17 的卡 | 再提交一组图片；分别在两张卡上驳回、锁定 | 公开面保持上一版；L4 队列移除；后续 diff 不得把被拒图片当待审内容 |
| C20 复审期间撤回 | C17 的卡 | 提交一组图片后在属主端「还原图片」 | pending 页清空、L4 队列消失、公开面不变；再次打开编辑窗无待审残留 |
| C21 驳回后重新提交 | C19 驳回的卡 | 属主重新提交另一组图片 → 后台通过 | 上一轮被拒的页面/对象不混入新修订；公开面只出现新集合 |

## 6. 遗漏与风险

1. **管理端中间页旋转的索引**：`rotations.middles` 与 `media_order` 的中间槽位一一对应，末尾的空转
   会保留以避免下标错位；测试时用至少 4 页卡并旋转最后一张中间页，确认背面没有被误转。
2. **单面卡的 `null`/`undefined` 背面**：七个列表与四个窗口都要看一次单面卡，确认不会渲染
   幽灵背面或必 404 的占位图（响应里背面可能是 `null`，也可能整个字段缺席）。
3. **补充/认领的「旋转」与审批落库是两条路径**：旋转生成页面对象后，必须在审批完成时把
   `pages` 一起提交（claim/supplement completion），否则公开面仍是旧图；C11/C12 必须刷新后复核。
4. **投稿审核通过要把 pending 页提升为 live**：`publishStagedRevision` 现在会清掉旧 live 页并
   把 pending 页整体提升（已有 `fudaba.test.ts` 回归用例）；C14 仍要刷新墙与主页确认不是旧版本。
5. **`pendingPages` 只在属主详情/编辑窗可见**：公开列表即便卡有待审图也必须显示线上版本；
   用同一张卡在 L1 与 L2 对照检查。
6. **页数边界**：1 页、2 页、3 页、>3 页的角标与页签逻辑不同；C1/C2/C3 已覆盖，回归时不要
   只测双面卡。
7. **旧数据回退**：迁移完成后测试环境所有卡都有页面行，`front_object_key` 回退路径不会自然
   触发；如需验证，只能临时构造「只有列、没有页行」的卡，属于开发验证，不建议进测试环境。
8. **不改变媒体的操作不必重复看图片**：锁定/解锁、仅文本补充、反馈、非公开可见（改回后）都只
   验证列表与状态；图片断言沿用同一张卡的上一次状态即可。
9. **缓存**：同一槽位连续旋转两次，第二次必须拿到新版本；`?w` 缓存键包含页面版本，若第二次
   仍显示第一次的图，说明版本没有变化或缓存头错误。
10. **删除后的孤儿对象**：P5 引用集 GC 尚未上线，删除/替换后的旧对象仍留在存储里；本验收只看
   界面，不把「对象仍存在」当失败。

11. **复审驳回/锁定后的 pending 页**：驳回只改审核状态，不清 pending 页行。C19/C21 要重点确认：
    驳回后重新提交、或驳回后只改文本再提交时，旧 pending 页不能混进新的待审集合；若出现旧图回流，
    需要补一步「驳回时丢弃 pending 页」的清理。
